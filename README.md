# Jobradar · connected job memory

[![CI](https://github.com/isjiajia01/jobradar-relate/actions/workflows/ci.yml/badge.svg)](https://github.com/isjiajia01/jobradar-relate/actions/workflows/ci.yml)

Explainable job recommendations, remembered in a single-file Relate graph.

Why does the same Data Engineer opening score **95 on one board and 60 on another**? The synthetic profile has seen and liked `j01`, which was published before `j02`. A cross-board similarity edge connects the listings. The later posting gets a repost penalty. Both scores carry the graph evidence that produced them.

This solo entry for the *Relate by Neo4j Hackathon* explores a memory layer for a personal job digest. All listings, profile choices and outcomes in this repository are synthetic.

## Use case

I keep a personal daily LLM job digest (Jobindex, Jobnet, LinkedIn). It scores each posting from one description, so it forgets what I liked or dismissed, cannot see that boards repost the same opening, and cannot explain a score. The relationships that matter: job to skills, job to company, job to similar listings on other boards, and my verdicts on neighbouring jobs. This repo is a synthetic prototype of that memory layer.

## How it uses Relate

- **Mode:** single file (embedded, in-process; no server, no signup).
- **Why this mode:** one file per user is easy to back up, commit and inspect. Judges can open the exact store, `jobradar.rl`, with the `relate` CLI or the Python client. It is persistent, not `:memory:`.
- **What the graph models:** `Job`, `Company`, `Skill`, `Location`, `User`; edges `AT`, `POSTED`, `REQUIRES`, `IN`, `SIMILAR_TO {score}`, `LIKED`, `DISMISSED`, `SEEN`, `HAS_SKILL`, `RELATED_TO`. Details below.
- **Relate capabilities used:** embedded Python client (`relate-db` 1.2.0), CLI (`--read-only`), Cypher with bound parameters, persisted full-text index and `SEARCH`.

## Where the data lives

`./jobradar.rl` in the repo root (about 48 KB, synthetic). `make build OUT=<new path>` rebuilds an equivalent store from `data/sample_jobs.json` and `graph/profile.cypher`.

## Setup and run

Prerequisites: Python 3.12+ and `make`. The Relate CLI v1.2.0 ([relatedb.ai](https://relatedb.ai)) is optional for the judge targets. No API key, server or model download.

```bash
make demo                          # ranks 10 jobs, writes docs/demo.html
make replay JOB=j05 VERDICT=LIKED  # flip a verdict on a temp copy, see what moves
make why JOB=j06                   # itemised score and evidence path, read-only
make search QUERY=engineer         # Relate full-text SEARCH, then rank by fit
make test && make eval
make similar JOB=j06               # optional: toy lexical vector search plus graph evidence
make scale N=500                   # optional: synthetic scale timings
```

Real output (the committed `jobradar.rl` is never modified):

```text
$ make replay JOB=j05 VERDICT=LIKED
j05 45 -> 80
j06 50 -> 75
  User -DISMISSED-> j05 -SIMILAR_TO(0.8)-> j06 (same company: Havn Pay)   # before
  User -LIKED-> j05 -SIMILAR_TO(0.8)-> j06 (same company: Havn Pay)       # after

$ make why JOB=j06
j06 score 50
  +50 base
  +10 skills 1/3 matched
  +5 related skills x1
  -15 dismissed similar x1
```

The other eight scores do not move. **Zero-install view:** [jobradar.isjia.page](https://jobradar.isjia.page/) is the static page generated by `make demo` (ranked cards, score breakdowns, default replay). It is a static export, not Relate running in the browser. `docs/demo.html` shows ranked cards with score breakdowns and the default replay. `make similar` uses a toy hashed bag-of-words vector index, not a semantic model ([docs/vector.md](docs/vector.md)). `make scale` times a seeded synthetic graph and is no real-world evidence ([docs/scale.md](docs/scale.md)). More targets: `make help`. Graph and scoring details, plus the optional LLM scorer: [docs/design.md](docs/design.md).

## Real job catalog (no similar-listing links)

`make real` ranks 50 real public postings from the MIT-licensed Djinni dataset (see `DATA-NOTICES.md`) on a temporary graph. Only the **catalog** is real. The profile is still invented, and skills come from a 40-word keyword list we wrote, applied to truncated descriptions, so some are missed. The sample is skewed towards "Big Data" titles because of how the dataset is ordered. **This catalog has no `SIMILAR_TO` links:** Djinni is a single source and our similar-listing rule needs the same company on two boards. So repost detection and feedback replay are demonstrated only on the synthetic fixture. There is no duplicate label in Djinni either, so the evaluation is not run here.

## Optional read-only MCP recipe

With the Relate v1.2.0 CLI on `PATH`, configure your MCP host to launch the absolute path to `scripts/mcp-readonly.sh` over stdio. From the repository root, its command is `relate serve --database jobradar.rl --mcp stdio --read-only`. The judge targets work without MCP.

We called `get_schema` with `{}` and `read_cypher` directly over MCP stdio on a temporary copy of the shipped store. That checked the protocol and tools. We then ran one session with Claude Code (2026-11-20, `claude -p` with a `--mcp-config` pointing at the script): the agent called `get_schema` and then `read_cypher` twice, and correctly reported that j06's only `SIMILAR_TO` neighbour is j05 and the user's LIKED/DISMISSED edges. One session, read-only; the store's checksum was unchanged afterwards. Other hosts were not tested. Pass each query below as the `statement` argument to `read_cypher`.

**Which dismissed listing contributes to j06’s penalty?** The result is `j05`, `DISMISSED`, similarity `0.8`, at Havn Pay. That same-company feedback costs j06 15 points.

```cypher
MATCH (:User {id:'me'})-[v:DISMISSED]->(peer:Job)-[s:SIMILAR_TO]-(j:Job {id:'j06'})
MATCH (peer)-[:AT]->(c:Company)<-[:AT]-(j)
RETURN peer.id AS peer, type(v) AS verdict, s.score AS similarity, c.name AS company
```

**Which Jobindex listings has the profile seen?** The result is `j01`.

```cypher
CYPHER 25 MATCH (:User {id:'me'})-[:SEEN]->(j:Job)
FILTER j.source = 'jobindex'
RETURN j.id AS job ORDER BY job
```

## Evaluation and limits

Small and fixture-specific. On six author-labelled pairs the graph scorer gets **6/6** and skill overlap alone **4/6**; the labels mirror the scorer's signals, so this is a regression check, not evidence of general ranking quality. Repost identity: **5/6** on the original synthetic feeds and **3/5** on cases written after the rule was frozen, with a known false positive for identical roles on separate teams. Ten synthetic jobs and one profile. Full detail: [docs/evaluation.md](docs/evaluation.md), [eval/results.md](eval/results.md).

## Origin, disclosure and AI use

- **Started during the contest:** all code in this repository was first committed on 2026-11-20, after the contest began. No code was copied from my earlier private Jobradar project; only the idea (a daily job digest with LLM scoring) carries over. Jobradar is a personal tool, not an employer or production system.
- **Data:** every job, company and profile choice is synthetic. No real feedback or other people's data is included.
- **AI tools:** the repository was written with AI coding agents under my direction, running in the Pi coding-agent harness. I chose the scope, approved each step and checked results. The optional LLM scoring path calls an OpenAI-compatible endpoint; the judge path uses no model.
